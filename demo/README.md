# ContentSeeder Demo

A working Optimizely CMS 13 site that demonstrates the full feature set of `TechnicalDogsbody.Optimizely.ContentSeeder`. It seeds a trail-shop site in three languages (English, Chinese and Arabic), with pages, shared blocks, Visual Builder experiences, an article listing with paging, videos, real placeholder images, and content area assignments.

For full package usage documentation, see [../README.md](../README.md).

## Two demo sites

| Demo | Project | CMS | URL | Database |
|------|---------|-----|-----|----------|
| CMS 13 (this page) | `TechnicalDogsbody.Optimizely.ContentSeeder.Demo` | Optimizely CMS 13 | `https://localhost:5000` | `EPiServerDB` |
| CMS 12 | `TechnicalDogsbody.Optimizely.ContentSeeder.Demo12` | Optimizely CMS 12 | `https://localhost:5001` | `EPiServerDB12` |

The Aspire host starts both against one SQL Server container, each with its own database. The CMS 12 demo is a smaller version of this one: pages, shared blocks and an article listing, with no Visual Builder sections or Experience pages, because those do not exist in CMS 12. See [the CMS 12 demo](#the-cms-12-demo) below.

## What gets seeded

The master language is English (`en`). The main demo seed also seeds `ar-AE` (Arabic). Its languages are set on the definition itself (`MasterLanguage` and `Languages` in `Seeding/DemoSeedDefinition.cs`), which override `ContentSeeder:MasterLanguage` and `Languages` in `appsettings.json` for that seed. The live demo seed sets none, so it uses `appsettings.json`. To seed another language such as `zh`, add it to the definition's list and enable it in the CMS. Every page and block has a version in each language.

| Content | Count | Notes |
|---------|-------|-------|
| StartPage ("Home") | 1 | Hero banner, plus a promo area of 12 blocks: 4 promo and 8 video |
| ArticlePage under Home | 3 | Dated, newest first |
| ProductPage under Home | 3 | Each has one "Care guide" article under it (3 in all) |
| ArticleListingPage ("The Trailhead journal") | 1 | Lists its 15 journal articles, 6 per page, so 3 pages |
| Kitchen sink article (ArticlePage, named set `kitchenSink`) | 1 | The body uses every common rich text tag, in a fixed order, for checking how they render. Its title and body come from the named set. |
| LandingPageExperience | 4 | Two full layouts, one of shared leaf sections only, one with no layout at all |
| CampaignPageExperience | 1 | Places the same CTA section twice, and a kitchen-sink section |
| HeroBlock / PromoBlock / TeaserBlock | 1 / 4 / 2 | Shared blocks, referenced from the start and product pages |
| VideoBlock | 8 | Each shows a different way of choosing a video (see below) |
| Shared sections | 5 | Created once and referenced: hero, CTA, feature cards, testimonial, video |
| Inline sections | 3 | Built fresh on each Experience: a blank section, a kitchen-sink section, an empty one |

Text in a language with a generator rule (for example the landing page heading, the campaign names, and button labels) comes from that rule. Other text is generated by Bogus in that language where Bogus has words for it, and in English otherwise. If you configure an AI provider, the AI writes the prose from the writing brief instead.

**Videos** need internet access. The `Uploaded` video downloads a short clip from test-videos.co.uk the first time it is used, and the YouTube and Vimeo feeds are read from their public feeds, with no API keys.

## Prerequisites

- [.NET 10 SDK](https://dotnet.microsoft.com/download/dotnet/10.0)
- [Node.js](https://nodejs.org) — building the CMS 13 demo builds the admin UI with `npm`, so it needs `node` and `npm` on the path
- A SQL Server instance — see the three options below (Docker Desktop for the Aspire option)
- An Optimizely licence file for each demo you run (trial licences are available from [license.episerver.com](https://license.episerver.com))
- The Optimizely NuGet feed added to your sources:

```shell
dotnet nuget add source "https://nuget.optimizely.com/v3/index.json" -n Optimizely
```

## 2. Set up the database

Choose one of the three options below.

### Option A — .NET Aspire (recommended, single command)

Docker Desktop must be running. No extra workloads or `dotnet workload install` steps are needed — Aspire ships as NuGet packages.

Skip the connection string setup entirely. Aspire provisions SQL Server automatically and injects the connection string into both demo apps. The host reads the SQL Server `sa` password from the `sql-password` parameter. Set it once, as a user secret, before the first run (use any strong password):

```shell
dotnet user-secrets set "Parameters:sql-password" "<a strong password>" --project demo/TechnicalDogsbody.Optimizely.ContentSeeder.Demo.AppHost
```

The SQL data lives in a Docker volume (`contentseeder-demo-sqldata`), so later runs must use the same password. To start again with a new one, remove that volume first. Then jump to step 3 (licence file) and run:

```shell
dotnet run --project demo/TechnicalDogsbody.Optimizely.ContentSeeder.Demo.AppHost
```

Aspire starts a SQL Server 2022 container, waits for it to be healthy, then launches both demo web apps. The Aspire dashboard URL is printed to the console (typically `http://localhost:15888`). Use the endpoint URLs shown in the dashboard for the demo apps.

### Option B — Docker (macOS / Linux / Windows)

**Step 1** — Start a SQL Server 2022 container:

```shell
docker run -e "ACCEPT_EULA=Y" -e "MSSQL_SA_PASSWORD=S33d3r_Sql!" \
  -p 14330:1433 --name contentseeder-sql -d mcr.microsoft.com/mssql/server:2022-latest
```

**Step 2** — Set the connection string as a user secret (keeps credentials out of source control):

```shell
cd demo/TechnicalDogsbody.Optimizely.ContentSeeder.Demo
dotnet user-secrets set "ConnectionStrings:EPiServerDB" \
  "Server=localhost,14330;Database=ContentSeederDemo;User Id=sa;Password=S33d3r_Sql!;TrustServerCertificate=True"
```

### Option C — LocalDB (Windows only)

LocalDB ships with Visual Studio 2022.

```shell
cd demo/TechnicalDogsbody.Optimizely.ContentSeeder.Demo
dotnet user-secrets set "ConnectionStrings:EPiServerDB" \
  "Server=(localdb)\mssqllocaldb;Database=ContentSeederDemo;Trusted_Connection=True;"
```

Optimizely creates and migrates the database schema automatically on first startup for all three options.

> **Upgrading from an existing CMS 12 database?** Point this demo at a brand-new, empty database
> rather than reusing one from before the CMS 13 upgrade. The CMS 12 → 13 schema jump is large, and
> a database that has accumulated ad-hoc schema drift from earlier development/testing can make
> Optimizely's own upgrade scripts fail with errors like `Cannot drop the index '...', because it
> does not exist` — those scripts assume a specific incremental history that a pre-existing dev
> database may not match exactly. This is not a ContentSeeder issue; there is no in-place fix
> beyond correcting the DB by hand. Dropping and recreating the database (or provisioning a fresh
> one via Option A/B above) resolves it, since CMS 13 creates its schema cleanly from empty.

## 4. Run the demo

If you are using Aspire (Option A), you already ran it in step 2. For Options B and C:

```shell
dotnet run --project demo/TechnicalDogsbody.Optimizely.ContentSeeder.Demo
```

The terminal prints the URL — typically `https://localhost:5000` for the CMS 13 demo.

### Testing against the packed NuGet packages

By default the demos reference the source projects in this repository. To test the packed packages instead, put the `.nupkg` files in `local-packages/` at the repository root (that folder is git-ignored).

The switch is `ContentSeederUseLocalPackages` in [demo/ContentSeederSource.props](ContentSeederSource.props). Change its default there (`true` for packages, `false` for source). The Aspire AppHost and both demos read that file at build time, so the AppHost follows it too. To override it for one build, pass it on the command line instead:

```shell
dotnet run --project demo/TechnicalDogsbody.Optimizely.ContentSeeder.Demo -p:ContentSeederUseLocalPackages=true
```

The version is set by `ContentSeederPackageVersion` in the same file (currently `0.1.0-rc.2`). Each demo clears its own generated `modules/_protected/TechnicalDogsbody.Optimizely.ContentSeeder` folder before every build, so output from the other mode doesn't linger.

To confirm which build a running demo uses, check the first lines of its console output (the Aspire dashboard shows them under the demo's logs). The CMS 13 demo prints:

- `[ContentSeeder] Built with ContentSeederUseLocalPackages=true` (or `false`), the switch the demo was compiled with.
- `[ContentSeeder] Loaded version 0.1.0-rc.2+<commit> from <path>`. Package builds show the package version. Source builds show a version generated from git, such as `0.0.0-alpha…`.

If you re-pack a version you've already restored, clear the cached copy first, or NuGet keeps using the old one:

```shell
dotnet nuget locals global-packages --clear
```

## The CMS 12 demo

`demo/TechnicalDogsbody.Optimizely.ContentSeeder.Demo12` is the same idea on Optimizely CMS 12, using the `TechnicalDogsbody.Optimizely.ContentSeeder.Connector.Optimizely12` connector. It runs at `https://localhost:5001`, and under Aspire it uses its own `EPiServerDB12` database.

It seeds a start page with a hero and promo blocks, three articles, three products (each with a care guide beneath it), and an article listing with 15 articles, which gives three pages of six. There are no Visual Builder sections, Experience pages or videos, so its seed definition (`Seeding/Demo12SeedDefinition.cs`) is much smaller.

- **Database schema:** CMS 12 does not create its schema on its own the way CMS 13 does, so the demo's `Startup` turns on `DataAccessOptions.CreateDatabaseSchema` and `UpdateDatabaseSchema`. Run on an empty database, it creates the CMS tables, the identity tables and the ContentSeeder table, so there is no CLI step.
- **Package versions:** the project does not use the repository's central package versions, which pin the CMS 13 line. It references `EPiServer.CMS` 12.24.0 and `EPiServer.Cms.UI.AspNetIdentity` 12.24.0 only, and lets the CMS package choose the matching CMS Core, Framework and Hosting versions. Pinning any of those separately mixes releases, and CMS then fails at startup with a missing stored procedure.
- **Admin user:** the first admin user is created on startup. Its password is logged once, or you can set `Demo:Admin:Password` as a user secret.

## 5. Log in

1. Navigate to `/Optimizely/CMS` — e.g., `https://localhost:5000/Optimizely/CMS` for the CMS 13 demo, or `https://localhost:5001` for the CMS 12 demo.
2. Log in with the auto-created admin account:
   - **Username**: `admin@example.com`
   - **Password**: set `Demo:Admin:Password` in user secrets to choose one. If you don't, a random password is generated on first run and written to the console log once, so copy it then.

`AdminUserInitializer` creates this account on first run if no users exist. Remove that class before deploying to any shared environment.

The SQL Server `sa` password used by Aspire (`S33d3r_Sql!` in the connection strings above) is a local development default. Don't reuse it anywhere else.

## 6. Seed the content

`SeedOnStartup` is `false` in `appsettings.json`, so the app starts without seeding. Seed from the admin gadget (step 7): open **Content Seeder** and click **Seed**. The status panel shows **Running for** while it works, and the counts update as pages are created.

Seed fills gaps, so running it again is safe. It creates anything that is missing and leaves existing pages alone. To rebuild everything from the current definition, use **Reseed**.

### What to check on the front end

Open `https://localhost:5001/`. Then check:

- **Home:** a hero banner, and a promo area with cards, including the videos.
- **All articles:** the listing "The Trailhead journal" shows six cards per page, newest first, with a numbered pager and Newer/Older links. Page 3 has the three oldest articles.
- **Product pages:** a teaser area, and a link to the care guide under each product.
- **Kitchen sink:** the article "Kitchen sink", and the "Every rich text tag" element in the campaign page's kitchen-sink section, show headings `h1` to `h6`, bold, italic, underline, strikethrough, sub and superscript, code, a link, a line break, `pre`, a quote, nested bulleted and numbered lists, a rule, a table and an image, in that order. Check each one is styled. The article bodies use the same kind of tags at random: some words are bold, italic or links (with Bogus), or the AI writes a subheading, a list and bold text.
- **Shared block folder:** in the CMS block tree under For All Sites, the seed's shared blocks are in `Seeded/demo-seed-v1`.
- **Landing pages:** one with a hero, a video and the content sections; one with only shared leaf sections, with styled slots; one with no layout, which shows only the header.
- **Campaign page:** the CTA section appears twice, and the kitchen-sink section shows every element type.
- **Chinese and Arabic:** open the same pages in the other languages (the CMS language switcher, or the language prefix in the URL). Arabic pages render right to left. The listing title, campaign names, hero and CTA labels, statistics and testimonial titles come from the language rules, so they differ from English.

To see the content tree in the CMS, open the content tree: `Home` is at the root with articles, products, the listing and the experience pages beneath it.

## 7. Manual seeder operations

The admin gadget gives you full control after initial seeding.

1. In the Optimizely admin navigation, open **Content Seeder** (requires `CmsAdmin` role).
2. The status panel shows tracked page, block and section counts. While a run is in progress, the **Last seeded** tile shows **Running for** with the elapsed time.

| Button | What it does |
|--------|-------------|
| Dry Run | Reports how many items a Seed would create or skip, without writing anything. |
| Seed | Creates any missing content, reusing existing pages where they match the definition. |
| Reseed | Deletes all seeded content and recreates it from the current definition. |
| Delete All | Permanently removes all seeded content and resets tracked counts. |
